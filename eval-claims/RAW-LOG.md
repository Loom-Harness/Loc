# Loom claims-system dogfood — findings log
## Iteration 1
- F1 `covers` is a reserved keyword → natural insurance name `function covers(...)` rejected (msg is good).
- F2 `create` body is INERT on state-based aggregates (loom.lifecycle-body-dropped, M-T3.16): can't default status, stamp reportedAt, or emit ClaimSubmitted on creation. Even docs' own Claim example hits this.
- F3 `status: X = Draft managed` → parse error "Expecting ':' but found `effectiveFrom`" (modifier must precede default: `managed = Draft`). Confusing message.
- F4 workflows can't read another context's repo (by design); the "local projection" alternative isn't shown in workflow.md.
- F5 Declared `create(...)` param list doesn't shape the wire: optional fields (approvedAmount, rejectionReason, assignedTo) are accepted on POST /claims → a client can create an already-approved-amount claim. Need `managed` on each op-only field. No warning when params are a strict subset that omits only optionals.
- F6 `retrieval OpenClaimsFor` emits NO HTTP route / client hook / UI. Yet `ddd new` starter teaches criterion+retrieval, and declaring one turns on `loom.repository-find-deprecated` for list finds in that context — the compiler steers you to the construct that can't be reached from the API.
- F7 **BUG (silent)**: cross-context enum (`Claim.kind: CoverageKind`, CoverageKind declared in Underwriting) → node output fails `tsc` (`Cannot find name 'CoverageKind'` in domain/claim.ts + claim-repository.ts); 0 Loom diagnostics. Docs (language.md §"Inside a system") promise cross-context enum refs "work freely".
- F8 env: generated Dockerfiles can't build behind the sandbox proxy (expected; certs/ hook exists). Ran api on host + pg in docker instead.
- F7b same root cause on react: cross-context enum → `defaultValues kind: ""` (tsc error) and rendered as free-text TextInput, not a Select.
- F9 UI: `X id` references render as truncated UUID chips ("01a107b6…") in list+detail, though validator FORCED me to add `derived display` to each target. Display is used only in pickers.
- F10 UI: enum badges truncated to "C…"/"Su…" in list table; list shows every column (id, description…) with no column selection hint.
- F11 UI: all operation buttons always shown (Approve on a Paid claim) — preconditions don't drive enablement; only a `when` header clause gets can_<op>.
- F12 UI: sidebar heading "AGGREGATES" — DDD jargon leaks into end-user UI; money shows "4200" without currency/format; description is single-line input.
- F13 runtime: op endpoints return empty 200 body — client must refetch. (fine, note)
- F14 runtime: claim with nonexistent policy id accepted (no FK across contexts even on the same DB); duplicate claimNumber accepted (my fault — `unique (claimNumber)` exists; not suggested by tooling though).
- Positive: happy path worked first time after patch; problem+json errors with custom `message`; money wire as string w/ scale 4; managed default stamping (`reportedAt`, `status managed = Submitted`) works; migrations auto-applied on boot.
## Iteration 2 (feedback: validate claim vs policy terms, adjuster capacity, deductible, fraud flag, unique numbers)

## Iteration 3 (feedback: login + roles, only assigned adjuster approves, >10k needs supervisor, separate Payments service on python over redis, payment → claim Paid)
- F30 `requires … message "…"` not in grammar (precondition has it) — 403s can't explain themselves.
- F31 **design gap**: operations a workflow needs (Claim.intake sets deductible+fraud flag; CoveredPolicy.deactivate; Claim.markPaid for the payment reactor) must be PUBLIC HTTP routes — workflows can't call `private operation` (loom.workflow-private-operation). Workaround `requires Nobody()` (policy = false) — still a public 403 route + a UI button.
- F32 a named `policy` fn in a workflow header `requires CanManageStaff()` → scaffold copies it into UI page gates, which reject `call` (loom.page-gate-not-client-evaluable), though the policy body is itself client-evaluable — the browser renderer doesn't inline policies the way the server does. Must inline by hand.
- F33 **BUG (silent)**: a policy declared in ClaimsHandling used in an Underwriting `find … requires` → node emits `CanHandle()` undefined (tsc). Same-context policy is inlined fine.
- F34 **BUG (silent)**: python deployable `payments` (doesn't host ClaimsHandling) + system `user { adjusterId: Adjuster id? }` → `app.auth.user`/`oidc.py` import `ids.AdjusterId` which isn't emitted (ImportError at boot; mypy attr-defined). Also `app/http/workflows_routes.py` uses `User` without importing it (mypy name-defined).
- F35 deny-by-default diagnostics are excellent: listed every ungated route, explained crudish(requires: Policy), create-gate placement, and the ungatable synthesized by-id reads.
- F36 by-id reads (`GET /claims/{id}`) can't be gated — any authenticated user (incl. a future policyholder portal) can read any claim (warning only).
- F37 generated Keycloak realm: demo user has role=admin, `adjusterId: "demo-adjuster-id"` (not a uuid), NO `permissions` and no `aud` claim → under denyByDefault the demo user can do nothing / is rejected once audience is set. KC26 also drops unmanaged user attributes created via admin API unless `unmanagedAttributePolicy` is enabled in the realm — generated realm doesn't enable it, so adding users with `permissions` silently yields tokens without them.
- F38 **semantic inconsistency**: an operation's `requires` gate is re-evaluated when a WORKFLOW calls it (so `requires Nobody()` blocks the workflow too), but the aggregate `create { requires … }` gate is NOT evaluated when a workflow calls `Agg.create(...)`. Combined with F31 there is no way to express "internal op only callable from a workflow".
- F31b demonstrated: alice (claimsHandle) POSTed `/claims/{id}/intake {"deductible":"0","fraud":false}` → 204; the payment then went out at 2500 instead of 2300.
- F39 **BUG cross-backend**: `audience: env("OIDC_AUDIENCE")` with the env unset: node treats "" as "skip aud check", python passes `audience=""` with verify_aud=True → EVERY token rejected (401) and the exception is swallowed with no log. Compose doesn't set OIDC_AUDIENCE and the realm has no audience mapper, so following the compiler's own `audience` warning breaks python auth out of the box.
- F40 **BUG (silent → runtime)**: an event-triggered workflow (`create(e: PaymentSent) by e.claim`) calling a `requires`-gated op → node emits `currentUser` that doesn't exist (tsc error; runtime `channel_consume_failed: currentUser is not defined`). No validator. No "system principal" concept for reactors.
- F41 failed channel consumption is logged as warn and dropped (default retention ephemeral) — claim stuck in Approved forever; no retry/DLQ by default, no hint in compiler output.
- F42 403 problem+json `detail` echoes the raw gate source (`Forbidden: amount <= money("10000") || currentUser.permissions.contains(...)`) — leaks authz internals to clients.
- Positive: OIDC (Keycloak realm, compose service, PKCE routes) generated out of the box; gates enforced correctly incl. row-relative `assignedTo == currentUser.adjusterId`; cross-service node→redis→python→redis→node eventing worked first time once auth was sorted; python migrations auto-applied.
- F43 a `tests/claim.ddd` file is silently ignored until `import`ed from main.ddd (no "orphan .ddd file" hint), though docs say tests may live in `tests/*.ddd`.
- F44 `ddd parse` prints raw Chevrotain "Ambiguous Alternatives Detected: <0, 1> in <OR1> inside <PostfixSuffix> Rule…" to the user once a test with `toThrow(precondition)` is in the project — grammar ambiguity leaks to stdout.
- F45 `toThrow(precondition|invariant)` is refused when the rule carries a custom `message` — rung detection is by message-prefix string on 4/5 backends, so good error messages and precise tests are mutually exclusive.
- F46 **BUG (false green)**: unit test with cross-context enum literal `kind: Fire` emits bare `Fire` (ReferenceError). `expect(Claim.create({... Fire ...})).toThrow()` therefore PASSES for the wrong reason — a codegen bug masquerades as a passing negative test.
- F47 **BUG**: `expect(c.payout).toBe(money("-100"))` → vitest `toBe(new Decimal("-100"))` (Object.is) — always fails: "expected -100 to be -100". Money equality in tests needs `.equals`/`toEqual`.
