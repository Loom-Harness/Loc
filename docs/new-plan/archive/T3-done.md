## M-T3.17 — The tenancy subtree read is correct but no longer index-usable — `done` · **M** · P2

**Context.** The `deep`/`global` descendant test used to be `data_key LIKE <anchor> || '.%'`, which rode the `text_pattern_ops` index the tenancy migration derives (`tenant-index.test.ts`). That spelling was a **cross-tenant read**: the anchor is a principal claim, so `_`/`%` inside it were LIKE wildcards, and an org named `acme_corp` matched `acmeXcorp.…`. #2562 fixed it by anchoring the test instead — `strpos(data_key, <anchor> || '.') = 1` — which has no pattern language and so needs no ESCAPE discipline. Correct, and **not sargable**: Postgres cannot use a btree/`text_pattern_ops` index for a function-of-column predicate, so every deep/global read became a sequential scan.

**Shipped (#2656) — option 1, but as a PREFILTER rather than a replacement.** The descendant test is now two terms, identical on every backend that renders the `scope` sentinel:

```
data_key LIKE <escaped-anchor> || '.%' ESCAPE '!'   -- sargable prefilter
  AND strpos(data_key, <anchor> || '.') = 1         -- unchanged from #2562; decides the row
```

Keeping the anchored test as a **conjunct** is what defuses option 1's stated risk ("an escaping bug reintroduces the leak silently"): a LIKE-escaping mistake can only make the prefilter *wider*, and the recheck then discards the extra rows, so the `orgXa.leak` trap is green by construction, not by trusting five escape helpers. Measured, not asserted: the planner rewrites the escaped LIKE to `data_key ~>=~ 'org_7.' AND data_key ~<~ 'org_7/'` and takes a Bitmap Index Scan on `accounts_data_key_idx` (cost 232) where the `strpos`-only form was a Seq Scan (cost 607).

No DDL or collation change was needed — the `text_pattern_ops` opclass P2.5 already derives is exactly the index a prefix LIKE rides under any collation. Option 3 (half-open range) was rejected for the reason the mission flagged: `data_key >= a || '.' AND data_key < a || '/'` is the descendant set only under the C collation, and every ORM's `>=` uses the column's collation, so it would have meant an `ALTER … COLLATE "C"` across two migration emitters with a silent false-negative failure mode. Option 2 (`^@`) needs a second index kind and is not expressible in JPQL/EF LINQ without raw SQL.

Escape character is `!`, not `\` — the pattern is spelled in five generated languages plus HQL, and backslash is the one character whose literal meaning differs between them. The five escape chains live together in `src/generator/_expr/subtree-like.ts`.

**Verification.** `test/e2e/tenancy-subtree-explain.test.ts` (`LOOM_TENANCY_E2E=1`) builds the schema from the emitted migration SQL, lifts the predicate verbatim out of a generated repository, seeds 20k rows, and asserts `Index Scan`/`Index Cond` on `accounts_data_key_idx` for both the MikroORM and Ecto spellings. `test/ir/tenancy-subtree-prefix.test.ts` pins the negative half per backend (no LIKE without an ESCAPE clause; no pattern built from a raw claim); `test/generator/policy-deep-scope.test.ts` pins prefilter-AND-recheck on all five. The `orgXa.leak` trap in `assertHierarchyIsolation` is unchanged and still green.

Sources: the leak and its fix are [#2562](https://github.com/lemmit/Loc/pull/2562); the sargability loss was flagged in the #2521 review; the fix is [#2656](https://github.com/lemmit/Loc/pull/2656).

## M-T3.16 — The lifecycle write gate: the canonical `create` / `destroy` body — `done` (2026-09-28, Wave C5 moment 5b) · **M** · P1 (security)
The write-side twin of M-T3.15's read surface. A `requires` inside a canonical `create` / `destroy` is lowered into `canonicalCreate.statements` / `canonicalDestroy.statements` and read by **no backend** — so an authorization-gated create parses clean and leaves the route **OPEN**, and a `precondition` / `emit` / value-changing `assign` vanishes with it. [#2446](https://github.com/Loom-Harness/Loc/pull/2446) closed the SILENCE (`loom.lifecycle-body-dropped`, with four exemptions that are the design) but not the gap; [#2487](https://github.com/Loom-Harness/Loc/pull/2487) adds the guard's readable-surface contract (`create` → `currentUser` only; `destroy` → `currentUser` + `this`; neither → a parameter) as a CHECK, after the first emission attempt ([#2450](https://github.com/Loom-Harness/Loc/pull/2450), withdrawn) assumed that contract and emitted an unbound receiver on all five backends. Two things gate the re-emission: an enforcement gate that can actually FAIL (#2450's passed four seeded mutations — polarity inversion on three backends, and .NET's destroy gate moved after the delete), and a decision on Elixir, whose scaffolded **LiveView calls the context directly**, around any controller-level gate. Also open and independent: a **value-object-typed field default emits non-compiling code** at the wire boundary (the domain class rendered into the wire DTO — `mypy --strict` and CS0246; TS compiles by structural typing alone), and an event-sourced create's guard renders into a domain `_init` that cannot reach a principal. [#2443](https://github.com/Loom-Harness/Loc/pull/2443)'s `src/ir/util/op-gates.ts` and the route-builder unification (#2459–#2462) are the enablers: the DECLARATION half collapses to one edit in `api-surface.ts`, and the emission must reuse `op-gates.ts` rather than spell the same gate twice.

**Steps 2, 3 and 5 of the plan LANDED — the gate is emitted and enforced on all five backends** ([#2519](https://github.com/Loom-Harness/Loc/pull/2519)). Placement is each backend's own chokepoint rather than one rule imposed on all: Hono / FastAPI in the route, .NET in the Mediator command handler (its controller is a thin dispatch), Java in the service, **Phoenix in the CONTEXT** — the settled answer to the plan's first open decision (S1/A1). Phoenix is the only backend whose frontend runs in-process, so a controller gate there has a second front door: the scaffolded LiveView's new-form submit calls `<Ctx>.create_<agg>` and a `DestroyForm` calls `<Ctx>.destroy_<agg>!`, neither through a controller. The principal is threaded as an explicit `current_user \\ nil` argument (a LiveView is a separate process, so neither `conn.assigns` nor `Process.put` reaches it — an ambient-principal gate would fail closed on every LiveView write and silently break the default UI), and a nil principal DENIES rather than raising `BadMapError`, so a principal-less internal caller gets the typed `{:error, {:forbidden, …}}` its `with` chain already handles instead of a 500. The emission reuses `op-gates.ts` (`lifecycleGates`, which collects EVERY `requires` in a lifecycle body rather than the leading run — the other statements there are all exempt no-ops, so a trailing gate is still a real gate), and the DECLARATION half is the single shared-table edit #2443 predicted: `errorStatuses("create"|"destroy", guarded)` + `api-surface.ts`, from which all five backends' OpenAPI already derive.

**Step 3 landed with it**: an event-sourced lifecycle guard is REFUSED by name (`loom.lifecycle-guard-event-sourced`) rather than rendered into a domain `_init` with no principal in scope — where `currentUser` is a free identifier, so the guard did not deny, it did not compile. The false premise the ES exclusion rested on is gone.

**Evidence.** `test/generator/lifecycle-guard-render.test.ts` reads the emitted HANDLER (not the emitted spec — a backend can publish 403 and still let the request through, which is why the declaration gate could not have caught the original bug): each gate line is pinned BYTE-EXACT, so polarity, receiver and 7807 `detail` all fail as one assertion, and ordering is asserted by index (create before the factory; destroy after the load, before the delete and any audit staging). **Mutation-proven 10/10**, including all four defects #2450's gate passed: polarity inversion on Hono / Python / Elixir, and .NET's destroy gate moved below the delete — plus a gate deleted outright, a create gate moved after the factory, a wrong destroy receiver, the Elixir gate left in the controller only, an ungated create that becomes gated, and the dropped nil-principal safety. `test/fixtures/corpus/lifecycle-guard.ddd` carries the four shapes (principal-only create gate, principal+row destroy gate, an UNGATED create as the control, and a principal-ONLY destroy gate — the shape that strands a receiver binding, C1) through all five compile tiers; `test/e2e/fixtures/elixir-vanilla-build/vanilla-lifecycle-guard.ddd` adds the `ui … with scaffold` the corpus fixture cannot carry (four of five backends mount no ui), so the LiveView door itself compiles under `--warnings-as-errors`.

**What is LEFT (re-verified 2026-09-14) — ONE golden, no gaps.** **C4 is closed** (wave C2 packet 2f): `test/generator/lifecycle-forbidden-remap.test.ts` pins `httpStatus Forbidden -> 451` moving BOTH lifecycle rungs, per ROUTE, on all five — measured first, and all five already emitted it correctly, so the row was a missing golden rather than a gap.
