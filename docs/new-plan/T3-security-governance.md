## M-T3.15 — The read surface: system reads, projection masking, and the find teardown — `open` (D-READ-SURFACE-ORDER applied by default 2026-09-13: projection masking first, then the two small gates, then the system-read construct) · **L** · P1
Grew out of M-T3.2 item 3: once the `requires` gate stopped living in the domain entity ([#2443](https://github.com/Loom-Harness/Loc/pull/2443)), "so what secures the READS?" had no coherent answer. Four root causes, code-verified against `main` @ `1f917ac`. **(A) Loom has no construct for SYSTEM READS** — audit history borrows `find all`'s gate, workflow-instance reads (`/workflows/<wf>/instances`) are ungated AND invisible to `validateDefaultDeny`, and provenance is a write-only substrate with no read endpoint at all: three compiler-owned reads, three different answers. **(B) The two read surfaces cannot compose** — `loom.field-mask-projection-source` makes gated projections and `mask unless` mutually exclusive, and the diagnostic's own remedy points authors back at the *ungated* CRUD routes. **(C) The generated default is the unsecured surface** — the scaffold binds `.all`, not a projection. **(D) The find teardown has a hard prerequisite**: `ensureHistoryFind` copies `find all`'s `requires`, so deleting `requires` from `FindDecl` first makes `loom.audit-history-ungated` unsatisfiable — it would instruct authors to write syntax that no longer parses. Also recorded: `find all(): T[] requires <expr>` was enforced on node/.NET and **silently dropped on java/python/elixir** (each special-cases `all` out of its named-find loop, then emits the list route without reading its gate); and `commandHandler`/`queryHandler` routes have no header gate and are not enumerated by `validateDefaultDeny` (an `extern` handler has no body, so no gate surface at all). **[#2523](https://github.com/Loom-Harness/Loc/pull/2523) landed the read-gate slice**: the `requires` keyword moved to the projection declaration header; folded projections gained an ENFORCED gate on both read-model routes across all five backends (`loom.projection-gate-without-source` deleted — its premise, that a folded projection has nothing to protect, was false); the list-read gate now enforces on java/python/elixir through one shared derivation (`src/ir/util/read-gates.ts`); and `validateDefaultDeny` enumerates both projection kinds. So (A)'s "ungated AND ungateable" member is gone and (B)'s two amplifiers with it — what remains of B is the launder itself. Two items still carry the load — projection masking and the system-read construct; two are small, independent and security-relevant — gating workflow-instance reads and the handler gate.

## M-T3.6 — `organizationContext` + tenancy final surface — `partial`; items (3)+(5) `done` (wave C5 5e); (2b) and (6) are `open`; item (6) (D-CROSSTENANT-ACK applied by default 2026-09-13: `policy { deny on X }` is the acknowledgment) · **L** · P2
The reconciled surface's 7 pinned decisions, re-scoped against fresh `main` (2026-08-11). **Three were already satisfied and need no work**: (1) `dataKey` is an ordinary `string?` `internal` field with no `DataKey` type and no magic member ops (`prelude.ts` `buildTenantOwned`); (4) reads stay principal-anchored — true by construction, every derived filter anchors `currentUser`; (7) no ambient row pronoun — `authorization.md`'s `resource`/`record` never shipped, and gates reference the row through `this` / a typed policy param. Do not re-open them; **verify, don't rebuild.**

**(2) the `startsWith` prefix operator — DONE.** It was `queryable: false`, so a prefix predicate was honestly rejected (`loom.find-where-not-queryable` / `loom.criterion-not-selectable`) and nothing in the language could express a subtree read. Now queryable on every SQL path — drizzle, EF Core (LINQ), Dapper, JPQL, JPA Criteria, SQLAlchemy, Ecto — lowering to an ANCHORED position test (`strpos(col, $p) = 1`, JPQL `locate(:p, col) = 1`, EF's one-argument `StartsWith`) rather than `col LIKE $p || '%'`, so a `%`/`_` in the prefix VALUE matches literally. It is the first BOOL-returning queryable intrinsic, which is a genuinely new shape: a scalar intrinsic only ever appears as a comparison operand, so drizzle's and JPA Criteria's predicate-position dispatch never reached their intrinsic tables and had to learn it. Runtime-gated by `test/fixtures/corpus/prefix-filter.ddd` (all five compile tiers + the behavioral tier + a node-minted wire golden), which asserts the delimiter trap (`root.` must not match `root_a`), wildcards-are-data, and the empty prefix; mutation-proven — swapping in the naive `LIKE` lowering fails it with `expected 5 to be 1`.

Found and fixed while verifying: **Dapper crashed codegen on every queryable intrinsic.** `DAPPER_SUBSET` declared the adapter fully-lowerable over the queryable subset while `whereToSql` had no intrinsic arm at all, so `criterion C of X = this.s.trim() == "a"` + `filter C` under `persistence: dapper` died with a bare `Error`, not a `loom.*` diagnostic (the `policy { deny }`-on-dapper shape of #2492). Java's `@SQLRestriction` static-filter renderer had the same hole. Both now consume one shared Postgres-text table (`src/generator/_expr/pg-intrinsics.ts`), joined to the intrinsic-completeness gate.

**(2b) retiring the `__loomDeepScope__` sentinel — still open, and it needs two MORE operators.** `deep`/`global` still lower to `authz-filter { kind: "scope" }`. Expressing that as an ordinary `filter` needs queryable **string concatenation** (`currentUser.orgPath + "."`) and queryable **`!= null`** on the internal `dataKey` column, because the sentinel's NULL-`dataKey` OR-fallback to the tenant floor (`DEEP_SCOPE_SEMANTICS`) is load-bearing — dropping it silently hides every pre-P2.3 row — and seven renderers pin the compound byte-for-byte. Size that as its own slice; the operator it was blocked on now exists.

**(6) `crossTenant` fail-closed — open, and it needs a design call first, not just a check.** There is no `loom.crosstenant-needs-policy`. But the proposal's own example (`policy { allow global on ExchangeRate }`) is currently REJECTED by the shipped `loom.policy-target-not-tenant-owned`, which restricts every ladder rule to `with tenantOwned` targets. So the explicit acknowledgment surface has to be decided — relax that check for a `crossTenant` target (where `allow global` is a pure acknowledgment, since `crossTenant` already means "no tenant filter"), accept `deny on X` as equally explicit, or mint a different clause — before the requirement can be gated. Two fixtures would need the new line (`tenancy-owned.ddd`, `policy-deny.ddd`). **Note the trap if the relax-the-check route is taken:** the ladder's `allow global` currently lowers to a `scope` sentinel over the `dataKey` and `tenantId` COLUMNS, which the `tenantOwned` capability provides and a `crossTenant` aggregate does not have — so admitting the rule must ALSO make enrichment treat it as acknowledgment-only and derive no filter, or the emitters reference columns that aren't in the table (a codegen crash or, worse, DDL-valid-but-wrong SQL). The `deny` half has no such problem — its always-false sentinel touches no column.

**(3)+(5) `organizationContext` + its switch gate — DONE (wave C5 moment 5e), accessor and gate in the same commits.** `organizationContext.orgPath` is an ambient peer of `currentUser` (one member; lowered to the derived principal member `currentUser.orgContextPath`, so it rides every backend's principal threading). The carrier is a request header, `x-org-context: <path>` (the proposal left it open; decision recorded in the 5e hand-off). Every backend's auth layer (node `authMiddleware`, .NET `UserMiddleware`, java `UserFilter`, python `AuthMiddleware`, elixir `Auth` plug) admits it only inside the caller's `orgPath` subtree (equal, or anchored under `orgPath + "."`), falls back to the principal's own scope when absent, and answers anything else — or any value on an orgPath-less principal — with a pre-body 403 logged as the catalog event `org_context_denied`. Validator-enforced: `loom.org-context-surface` (bare / other member / on a `ui`) and `loom.org-context-gate-unmet` (no `tenantRegistry` hierarchy, or a hosting backend deployable without `auth: required`). Runtime proof: the `org-context` cells of `tenancy-e2e` on all five backends (in-scope switch stamps the sub-scope `dataKey`, deep-visible from the parent, hidden from a sibling; out-of-subtree and forged switches 403 with no write; reads stay principal-anchored), mutation-proved on node / python / .NET. The prelude `tenantOwned` still stamps `currentUser.orgPath` — re-rooting it (synthesis decision 3 for every tenant system) is an owner call, see [docs/tenancy.md](../tenancy.md#organizationcontext--the-operating-scope-and-its-switch-gate). Hand-off: [`waves/handoffs/wave-c5-5e-orgcontext.md`](waves/handoffs/wave-c5-5e-orgcontext.md).

## M-T3.7 — Tenancy hardening tail — `partial` · **M** · P2
(a) **DONE** — see below; (b) **DONE** (verified 2026-08-05) — the runtime matrix already reaches elixir: `test:tenancy-elixir` / `test:tenancy-hierarchy-elixir` ship and `tenancy-e2e.yml` is a 10-cell matrix (all five backends × {flat, hierarchy}); (c) **DONE** — see below; (d) `loom.tenancy-claim-type-mismatch` **already ships** (`tenancy-checks.ts`), alongside `loom.tenant-owned-claim-type`; **(e) claim-TYPED capability fields** — the remaining half of (a), see below.

**(c) Landed — a malformed tenant claim reads empty instead of 500-ing.** Under `tenancy by user.<claim> of <Registry>` with a `guid` registry id and a `string` claim (`tenancyClaimBinding === "guid-from-string"`, the common JWT shape), the derived self-scope `this.id == currentUser.<claim>` bound raw token text straight against the id. An authenticated token carrying `tenantId: "not-a-guid"` therefore died in the uuid parser — `IllegalArgumentException` out of Hibernate query preparation, `Ecto.Query.CastError`, pg `invalid input syntax for type uuid`, SQLAlchemy `ValueError` — and answered an ordinary bad token with a 500 and a stack trace. It always failed CLOSED (no leak, no cross-tenant read), so this was about the response, not the isolation.

**.NET was already right** and is what the other four were ported to: `Guid.TryParse(…) ? new <Agg>Id(g) : null`, i.e. coerce in the host language and let a NULL match no row. Same shape as (a) with the roles reversed — there Java was the correct one and four backends needed porting. Each backend renders its own native fail-closed form (a UUID-shape ternary falling to Drizzle's always-false term; `Ecto.UUID.dump/1` → nil, compared through a `fragment` so the PK index still serves the read; `User.guid_claim` → `None` → `IS NULL`; a `<claim>AsUuid()` accessor on the Java principal → `= NULL`), all gated on one shared IR predicate, `guidFromStringSelfScope` — the single shape whose principal side can fail to parse.

Java's Criteria path is fixed in the same change: a `criterion` on the registry emits a `tenantScope(User)` Specification that bypasses the `@Query` reads, and it compared the `@EmbeddedId` *embeddable* to a raw `String` — broken for every claim, well-formed or not. It now navigates to `id.value` and binds through the same accessor.

Why it hid: the shape was in `tenancy-owned.ddd` all along; only the malformed VALUE was missing, because every claim the isolation harness sends is a real org id. The fix therefore lands the probe in `assertCrossTenantIsolation`, so all ten `tenancy-e2e` cells assert the STATUS (200 + `[]`, 404 by id) — asserting emptiness alone would pass on a 500, since the read already failed closed. Compile-verified on all five backends; per-backend generator suites pin that no read path binds the raw claim.

**(e) The claim's TYPE is still pinned, now that its NAME is not.** `tenantOwned` provides `tenantId: string` as a literal, so a system declaring `tenancy by user.orgId` where `orgId: guid` is rejected by `loom.tenant-owned-claim-type` rather than supported — the capability's column would have to be typed from the declaration the same way (a) taught its filter and stamp to bind from it. The workaround the diagnostic suggests (declare the claim `string`; guid values round-trip as text) is real and costs nothing today, which is why this is P3 rather than a defect: nothing is silently wrong, and the gate is honest. It becomes worth doing when a capability needs a non-string discriminator, or when capability fields gain declaration-dependent types generally. Note the asymmetry that makes it more than a rename: the registry self-scope already handles a guid claim (it compares against the registry's own guid id via `tenancyClaimBinding`), so today one half of tenancy accepts a guid claim and the other refuses it.

**(a) Landed — the declared claim now binds the `tenantOwned` stamp and filter.** The capability hardcoded `currentUser.tenantId` on the principal side of both, so `tenancy by user.<claim>` only ever worked for one claim name: a non-`tenantId` claim emitted a backend referencing a claim the principal does not have — a compile error on node/.NET/Java, a per-request 500 on Python/Elixir. It crashed rather than failing open (no cross-tenant leak), but the documented surface was unusable for every other name.

Two things kept it alive. `prelude.ts` carried a note claiming the tenancy validators verified the declared claim *is* `tenantId` — they never did; they check the claim EXISTS and that its TYPE binds, never its name. And all three tenancy fixtures declared the claim as `tenantId`, the one name that makes the hardcode accidentally correct, so the corpus compile tier, the 10-cell `tenancy-e2e` matrix and the behavioral tier were structurally incapable of observing it.

Fixed in **phase ⑥, not in the macro**: a capability is a prelude definition built at language-module init with no system in scope, so it *cannot* read the declaration — enrichment is where per-system facts get bound, and it already derives the registry self-scope from the same `sys.tenancy`. That asymmetry is what made the bug legible: both halves appeared in one generated project disagreeing, the registry reading `.orgId` while the tenant-owned aggregate read `.tenantId`. The rewrite is scoped to capability-derived nodes, so an author's own `currentUser.tenantId` survives (a principal may legitimately carry an unrelated field of that name). The ROW column stays `tenantId` everywhere — the capability owns it. Four backends also reached for the column constant on the principal side of their scope-sentinel renderer and now read it off the sentinel (`deepScopeTenantClaim`, twin of `deepScopeAnchorClaim`); Java already did this correctly.

Gated by `test/fixtures/corpus/tenancy-claim-name.ddd` — the first fixture whose claim is deliberately not `tenantId` — which joins all five compile tiers and the behavioral tier, with a wire golden minted from node. Compile-verified on all five backends and runtime-verified on node/PGlite (create → filtered read returns exactly the created row; a stamp/filter disagreement returns 0).

## M-T3.9 — Audit promotion: `audited` aggregate-wide + `logged` — `partial` · **M** · P2
Boolean `audited` ships on all five, ops AND lifecycle (verified 2026-07-13: `AUDIT_OP_BACKENDS` = `AUDIT_LIFECYCLE_BACKENDS` = all 5, `system-checks.ts:2464-2465`; the old plan's "gate claims node support that ships nowhere" note was stale).

**Landed — the aggregate-wide form `aggregate X audited { … }`.** Sits in the header region beside `crossTenant` (same category: per-aggregate participation in a compiler-owned facility — see the M-T5.17 sort-by-meaning amendment). Covers every **public** command action; `private` operations are never audited, which is the opt-out for an internal/high-churn command. **Resolved during lowering** into the per-command flags rather than threaded through emitters — `op.audited` is read at ~30 sites across the five backends with no chokepoint, so resolving early means every existing gate keeps working and a site that forgot to consult an aggregate-level flag cannot silently drop coverage. No new `AggregateIR` field. Verified generate-and-inspect on all five backends with zero emitter edits; corpus fixture `audited.ddd` puts it through the per-backend COMPILE tier. Validator warns when `audited` is declared on an aggregate with no public command action (an empty trail reads as authoritative while lying by omission). Also removed dead code: `auditedOpsOf`/`aggHasAuditedOp` were exported from the .NET/Java/Python audit emitters, called by nothing, and had drifted apart.

**The argument form `audited(actions|access|events|off)` is DROPPED — do not build it.** Each of its five options dissolves on inspection:
- `off` → unnecessary; `private` is the opt-out, and the aggregate-wide/per-command forms are alternatives rather than layered, so there is no default to negate.
- `actions` → it *is* the shipped default; `audited(actions)` ≡ `audited`.
- `access` (read-auditing) → **a different feature**: different table, different trigger point (query pipeline, not command boundary), different volume profile (writes on every read), different consumer. Needs its own mission and its own modifier on views/finds — `access` on an *operation* is meaningless, yet the paren form would admit it.
- `events` → **subsumed by `persistedAs: eventLog`**, which already gives a richer, replayable history. A second, weaker event-emission mechanism competing with real event sourcing.
- `containsPii` → **derivable** from the existing `sensitive(pii, …)` field tags; don't restate at the audit site what the field already declares.

Dropping it also resolves a head-on collision with **M-T5.17**, which removed the paren modifier form and codemodded the corpus for it — `audited(actions)` would have reintroduced exactly that syntax. `audited` therefore stays a boolean permanently.

**Remaining:** the `logged` marker (unrelated to audit; keep), and the AuditRecord snapshot enrichment. The read side — exposing `audit_records` as an entity-history view — was deliberately not part of the original mission; it is tracked in its own section below.

**The read path — shipped on all five.** `audit_records` had no read endpoint on any backend, so the write substrate existed with nothing consuming it. (`auditTableShape` into `MigrationsIR` — the prerequisite this note used to list — landed separately in #2325, and #2379 did the same for `provenance_records`; both are ordinary companion tables now.) Landed here: the platform-neutral `AuditEntry` wire shape + diff boundary (`src/ir/util/audit-history.ts`), a derived `find history(id)` injected in the auto-`findAll` enrichment slot (as `RepositoryIR.historyFind` — *beside* `finds`, not in it: `finds` has ~120 generic consumers that all assume a find reads the aggregate's own table, and a missed skip-guard would emit a broken route rather than fail), and `GET /<agg>/{id}/history` on **all five backends** (#2378 node + python, #2404 java, #2406 .NET, #2408 elixir), with the wire golden (`test/behavioral/wire-golden/audit-history.json`) minted from node as the answer key the rest diff against — each of the other four matched it with 0 divergences on a real boot. Because A≡golden ∧ B≡golden ⇒ A≡B, the `audit-history` corpus row reading `ALL` is a *proven* cross-backend equality, not five self-assertions.

Two ports carried backend-local wrinkles worth knowing. **Phoenix:** `at` is written through Ecto's `:utc_datetime` (second precision), so ordering by `at` alone ties for two commands inside one second — the query adds an `audit_id` (UUIDv7, time-ordered) tiebreak, which no other backend needs. **.NET:** the snapshot columns were the only place a backend diverged on how the shared `jsonb` DDL was *bound* — a serialized string rather than an object — so #2406 moved them to `System.Text.Json.Nodes.JsonNode?` and `docs/audit.md` now states the binding for all five as one rule (a porter indexes the snapshot; nobody parses). That change collided productively with #2412, which found that `mask unless` + `audited` never compiled on .NET at all (CS0128 — a fixed `__maskUser` pattern-variable name, declared twice in one handler body).

**The frontend half is DONE on all SEVEN frontends** (corrected 2026-09-14, wave C2 packet 2i — the paragraph that stood here was stale). The `Timeline` walker primitive (#2400), the API-client `history()` and the scaffolded History section (#2407, gated by #2411) all ship, and the section is no longer narrower than the primitive: `HISTORY_CAPABLE_FRAMEWORKS` (`src/generator/_walker/history-read.ts`) names react / vue / svelte / angular / phoenixLiveView / **feliz** / **flutter**, and a frontend joins that set only by collecting the derived `history(id)` read AND rendering `Timeline` — "the same day, or not at all", because a target that renders the primitive while binding the wrong read looks like it works. Re-verified by GENERATING a `scaffold`ed `aggregate Order audited with crudish` on each of the three targets this paragraph used to exclude: **feliz** emits its own `OrderHistory: Remote<AuditEntry list>` Model field (not `AllOrders`), an `Api.orderHistory` fetch batched into the detail page's `pageCmd`, and a native `Html.orderedList` Timeline; **flutter** emits `GET /orders/$id/history` in `reads.dart` and the section in `order_detail_page.dart`; **HEEx** assigns `:order_history` from its own `load_order_history/2` (not the list read) and renders the `orders-detail-history` card. Giving the clients a `history()` method is the explicit bill for putting `historyFind` beside `finds` — they iterate `finds`.

The authorization slice is done and is the load-bearing one — `before`/`after` store raw field values *unmasked* **on four of five backends** (the write happens server-side inside the transaction, while `mask unless` is per-caller) — **.NET diverged, and no longer does (closed 2026-08-31, W1b `dotnet-adapters`):** its audited command handlers projected snapshots through the *masked* serializer, so a masked field was recorded as `null` whenever the acting principal failed the predicate — the stored trail depended on *who* performed the write. `projectEntityArgs` now takes an `unmasked` option (`src/generator/dotnet/dto-mapping.ts`) that the four audit sites pass — create, destroy, the audited operation's `__before`/`__after` pair, and the workflow's inline audited op-call — so .NET matches the other four. The READ path is untouched: the wire projection still masks, and so does the history query that reads the trail back, so the redaction moved to where it belongs rather than vanishing. Pinned by `test/generator/dotnet/audit-snapshot-unmasked.test.ts` (mutation-proved: re-wrapping the projection fails "the audit snapshot still redacts by the writer's principal"). Beyond that, so an endpoint that skips the masking pass publishes every masked field's full change history. Three guards, each re-established explicitly: the read gate is **copied from the aggregate's `find all`** (ungated + `denyByDefault` → `loom.audit-history-ungated`); capability filters ride **entity reachability** via `findById` rather than a predicate on `audit_records` (which carries no tenant column), so a cross-tenant history 404s exactly as the entity read does; and a masked field's `FieldChange` is **dropped, not redacted** — "admin changed `salary`" is itself the leak. Field diffs are derived at read time from the two snapshots and exclude managed/stamp *and* token fields (`after` is captured post-save, so `updatedAt`/`updatedBy`/`version` differ on every entry). Only *successful* commands are recorded (`status` hardcoded `"ok"`, insert rides the transaction), so this answers "what changed", not "who tried" — stated in [`docs/audit.md`](../audit.md) rather than left to be discovered.

Fixed in passing, both pre-existing: **Python's `mask unless` never redacted a multi-word field** (`to_wire` writes the wire key verbatim, but `to_wire_masked` redacted `d[snake(name)]`, so a camelCase field kept its full value — every mask fixture used `salary`, one word, where the two spellings coincide), and **collection ops in a `test e2e` body were emitted verbatim** (`trail.first()` → `trail.first()`, which JS arrays do not have, so the suite died with a TypeError at the assertion rather than failing to compile).

## M-T3.19 — `denyByDefault` leaves the synthesised `GET /<plural>/{id}` completely ungated, and says nothing — `partial` (the diagnostic slice `loom.default-deny-by-id-ungated` landed; the gate SURFACE + five route emitters remain) · **M** · **P0** (raised 2026-09-29 by wave L0: C5 moment 5d made `denyByDefault` the language default, so the hole is on every auth model) · security

Found 2026-09-10 by the tracker dev-experience run (#2861, "Not fixed here"). Re-verified on `main` @ `4865581` with `auth { enforcement: denyByDefault }` + `user {}` + `auth: required` on the deployable, one aggregate, and `find all(): Product[] requires true`:

```ts

responses: { 200: …, 404: …, 422: … },

// GET /   — gated, because `find all` carries a `requires`
responses: { 200: …, 403: … },
if (!(true)) throw new ForbiddenError("Forbidden: find all");
```

The model validates `0 error(s), 0 warning(s)`. So the list read is gated and the single-record read of the same aggregate is open to any authenticated caller — under the enforcement mode whose whole promise is that nothing is reachable unless it is gated. The list read has a recourse (`find all(): T[] requires <expr>`, documented in `docs/auth.md`); the byId read has no surface to attach a gate to at all.

`with crudish` is the same shape on the write side and is being closed separately by #2877 (`crudish(requires: SomePolicy)`), after the maintainer rejected an inherited aggregate-level default gate — a default-deny rule invisible at the member it guards is the wrong trade. This mission must honour that ruling: the gate is **named at the declaration**, not inherited.

**The fix:** a surface that gates the synthesised single-record read — the natural spelling being the `find` the repository can already declare (`find byId(id: T id): T? requires <expr>`) recognised as *the* byId read and used for the route, so the recourse is the one already documented for `find all` rather than a new concept.

**Until then the hole is a diagnostic, not silence:** under `denyByDefault`, an aggregate whose byId route has no gate should raise `loom.default-deny-ungated` the way an ungated operation does. That is the smallest slice and should land first; it turns a silent open read into a refused build.

> - **Its own code, not an arm of `loom.default-deny-ungated`.** Every arm of that code names a `requires` the author can write — which is exactly why the arms that have no such surface (the injected `find all`, a macro-emitted projection) are exempted rather than reported.
> - **A WARNING, not an error.** With no gate surface in the language yet, an error would make every `denyByDefault` model unbuildable with nothing the author could do about it. When the `find byId(id: T id): T? requires <expr>` surface below lands, the check gains its `if (gated) continue;` and promotes to an error under the same code.
>
