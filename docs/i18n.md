# Internationalization

Every user-visible string in a generated UI goes through a catalog lookup, and
translations live in a `locales/` tree next to the `.ddd` source. This page
explains what is translated, how keys are formed, how the tree is laid out, how
the active locale is chosen at runtime, and which targets render a translated
locale. The `ddd i18n` command reference is
[`tools.md`](tools.md#i18n-translator-workflow-ddd-i18n); the `i18n { source }`
block and the `label()` / `plural()` intrinsics are in
[`language-reference/02-systems-and-topology.md`](language-reference/02-systems-and-topology.md#i18n).

## What is translated

- **Page and component text** — headings, button labels, table headers,
  placeholders, and interpolated templates. A template such as
  `` `Order {order.id}` `` becomes the ICU message `Order {id}`; a slot with no
  literal text has nothing to translate.
- **Menu labels** — an authored `menu { … }` entry is a catalog string.
- **Model-derived text** — type names, field labels, operation names, enum
  values and named rules, keyed by the model element rather than by the page
  that shows it, so a word used on six pages is one entry.
- **Design-pack chrome** — the fixed words a pack renders (`chrome.*` and
  `pack.*` keys), declared by the pack.
- **Whole sentences only.** Placeholders carry data, never words, so a
  translator controls word order and grammar. Counts use ICU `plural`.

The server never translates a response. A validation error carries a stable
`code` (the rule's identity key) with `params` and an English `detail`;
ProblemDetails `title` is static English. The client localizes from the code.

## Key families

| Family | Key shape | English default |
|---|---|---|
| Model identity | `<Ctx>.<Type>.<facet>[.<member>]` — facets `name.one`, `name.other`, `field`, `op`, `value`, `rule`, `message` | derived from the identifier (`humanize`) |
| Hand-written page text | `<Ui>.page.<Page>.<role>.<hash>`, `<Ui>.component.<Comp>.<role>.<hash>`, `<Ui>.menu.<role>.<hash>` | the literal |
| Chrome | `chrome.*`, `pack.*`, `field.*`, `problem.*` | the pack's / toolchain's text |

The `<hash>` is a 6-character FNV-1a content hash in base 36
(`src/util/content-hash.ts`): reordering a page never re-keys a string, and
rewording one re-keys it (delete the old key, add the new). `role` is the slot
the text sits in, so the same words in two slots stay two entries.

Model-identity text is written with the intrinsics:

```ddd
Heading { plural(Task) }     // key Projects.Task.name.other, default "Tasks"
Text { label(Task.title) }   // key Projects.Task.field.title, default "Title"
```

Both calls sit in a page or component body and never inside a backtick template
(`loom.model-text-in-template`): a placeholder carries data, never words. In the
generated React app:

```tsx
<Title>{t("Projects.Task.name.other", "Tasks")}</Title>
```

## The `locales/` tree

```
locales/
  en/Projects.json     # overrides of the source-language text (optional)
  fr/_chrome.json      # chrome.*, pack.*, field.*, problem.*
  fr/Projects.json     # keys of context Projects, prefix dropped: "Task.field.title"
  fr/WebApp.json       # keys of ui WebApp: "page.Tasks.heading.k2f…"
  .loom/source.lock/…  # BASE of the three-way merge
  .loom/review/…       # needs-review flags
```

One file per namespace — `_chrome`, `_system` (types declared outside every
context), a bounded context, or a `ui`. A locale file holds finished
translations only; an untranslated key is absent. English wording overrides
live in `locales/en/` (or `locales/<source>/` when `i18n { source }` names
another language), never in the model: they change the default every `t()`
carries.

## Workflow

1. `ddd i18n init main.ddd fr` — scaffold the locale.
2. Translate `locales/fr/*.json`, directly or through `ddd i18n export` /
   `import` (XLIFF or PO).
3. `ddd i18n sync main.ddd` — three-way merge after the source changed
   (BASE = the lock, OURS = the locale files, THEIRS = a fresh extraction).
   It follows declared `migration` renames and moves, flags translations whose
   source changed, and advances the lock.
4. `ddd i18n check main.ddd --strict` in CI — invalid ICU, placeholder or
   plural-form mismatches, untranslated keys, pending review flags.
5. `ddd generate system main.ddd -o out --locales locales` — emit every locale
   found into each target that has a translation runtime. `generate` never
   writes under `locales/`.

`ddd i18n init main.ddd en-XA` generates an accented, padded pseudo-locale;
text that stays plain ASCII in it bypassed `t()`.

## Runtime locale

The frontends resolve the active locale in this order: `?lang=<tag>`, the
`loom_locale` cookie (written by the locale switcher), `Accept-Language`, then
the source language. Each candidate is tried as the exact tag and then as its
base language (`fr-FR` to `fr`). A key missing from the active locale falls
back to the source-language default carried by the `t(key, default)` call.
Phoenix runs the same negotiation in a plug and again in the LiveView process.
The backends read `Accept-Language` into `RequestContext.locale`.

## Per-target support

| Target | Translation runtime |
|---|---|
| React, Vue, Svelte, Angular | `i18n.ts` + `locales/<locale>.json`, ICU via `intl-messageformat` |
| Feliz, Flutter | their own generated i18n module over the same catalog |
| Phoenix LiveView | gettext `.po` tree, ICU formatting for interpolated messages |
| Backends (node, .NET, Java, Python) | none: responses carry codes and English text, the client localizes |

The source language is declared with `i18n { source: "de" }` (default `en`); it
names the source catalog, the runtime fallback and `<html lang>`.
